# QC implementation plan

**Goal:** Implement the user's supplied `!qc` specification, publish to GitHub, and update VPS through DAY_LEN_VPS.bat.
**Architecture:** Conversation state is isolated per bot/actor/chat. A content adapter creates one immutable payload; a checkpointed campaign sends on the broadcast lane. Existing roster enumeration and additive release catalogs remain authoritative.
**Tech stack:** Node ESM, node:test, existing Zalo SDK and workload broker.
**Spec:** The four-section Vietnamese specification supplied in this chat on 2026-11-27.

## Constraints

- adminLevelHigh only, group and DM; one active session/campaign per bot.
- Selection and content each expire after 5 minutes. Per the user's follow-up, selection accepts direct chat from the initiator in the originating chat; replying to a listed page is optional.
- Only the initiator in the originating chat can supply content. Commands pass through unless replying to the content prompt.
- One original message, one DM per distinct UID, skip bot UID. No lossy fallback or ambiguous-result retries.
- Send sequentially at least 1 second apart; survive campaigns beyond 60 seconds.
- Durable per-recipient checkpoints; interrupted campaigns never resume automatically.
- Publish committed code and deploy via BAT; document actual live verification limits.
